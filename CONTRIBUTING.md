# Contributing to HTS

> Status: Draft guidance; HTS review pending. Owner: HTS team. Historical frontend baseline: 2026-10-02. Current edition: Unreleased.

Read the [onboarding guide](docs/phase-3-development/onboarding.md) and [coding standards](docs/phase-3-development/coding-standards.md) before changing the site. Preserve the existing visual language, localized copy, accessible controls and third-party attribution.

## Changes and review

1. Inspect Git status and the current branch before editing; retain unrelated local work.
2. Describe the customer-facing problem and keep source, resources and documentation consistent.
3. Build in Release and run the relevant [test cases](docs/phase-4-testing/test-cases.md).
4. Document actual results and unresolved issues. Screenshots demonstrate a state, not proof of the whole flow.
5. Prepare a focused commit or PR only within the repository owner's authorization. Use English as the principal explanation and include PT-BR.

Useful branch names are `feature/website-request-wizard`, `fix/mobile-layout` and `docs/project-lifecycle`; these are conventions, not claims that branch protection is configured. Prefer concrete commit messages such as `feat(brief): guide custom website requests`.

Use the [bug report questions](docs/phase-4-testing/bug-report-template.md) for defects. Report sensitive vulnerabilities through [SECURITY.md](SECURITY.md). Do not attach customer briefs, credentials or private screenshots to public issues. Review is owned by the HTS team; no automated approval, delivery promise or contributor license agreement is established by this document.
